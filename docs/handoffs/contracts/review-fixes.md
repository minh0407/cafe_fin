## Cross-actor recovery keeps one file

The FileStore idempotency namespace includes its actor. Previously, actor B
retrying the interrupted output of actor A used another namespace and could
create a duplicate core file before linking it to the same contract version.

The append-only contracts migration v2 creates `contracts_output_storage` with
one storage owner per `(version_id, format)` and a foreign key to that output.
Owner reservation follows successful rendering and durable byte staging, before
FileStore.put. Subsequent attempts use that stable storage namespace while
authorizing the **current recovering principal** in the writer transaction.
Disabling the original storage owner does not block another authorized operator
or administrator from completing the output. The domain audit records the
actual recovering actor; the stored owner is an idempotency namespace, not an
authorization identity or an impersonated login.

For interrupted v1 outputs that have bytes and a FileStore receipt but no owner
row, a read-only compatibility lookup of the exported core REQUESTS table finds
the existing files.put receipt by stable output key **and exact payload hash**
(bytes hash, size, category, original name and media type). The module never
inserts/updates core receipts. It reserves that receipt's owner, calls public
FileStore.put with current-actor authorization, and verifies stored bytes through
FileStore.read before recording success. This also recovers outputs first
generated by an actor different from the original snapshot creator. Fresh
outputs do not scan the legacy receipt registry.

There is no fabricated success result or bypass of disabled-account/permission
checks. Current authorization is rechecked at render entry and final return,
including when all requested files already succeeded. Stage, owner reservation,
FileStore receipt replay and domain finalization retain transaction-level
authorizers. Revoke-during-render still leaves zero newly staged bytes/files;
revocation before or during verification of a previously successful file returns
401 rather than a stale success response.

## UUID normalization

Contract and version UUIDs are normalized before any version/output query or
render receipt key/name is built. Uppercase forms return the same file map,
version list, bytes/hash and retry receipt as canonical lowercase forms. Draft
audit history uses the canonical ID returned by the verified draft lookup too.
